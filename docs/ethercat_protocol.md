# EtherCAT 通信协议

## 一、协议概述

EncosDriver 通过 EtherCAT 主站与 EtherCAT-CAN 网关通信，本质是 **CAN over EtherCAT**：
主站与网关之间通过周期性 PDO（过程数据对象）批量交换 CAN 报文，网关负责在对应的
CAN 总线上实际发送或接收这些报文。

```text
电机命令 → 输出 PDO → EtherCAT-CAN 网关 → CAN 总线
CAN 总线 → EtherCAT-CAN 网关 → 输入 PDO → 电机反馈
```

协议对上层与电机两侧都是**透明**的：

- 电机侧看到的是原始 CAN 帧（标准 ID、扩展 ID、CAN FD 等）；
- 上层控制程序看到的是还原后的 CAN 报文；
- EtherCAT 只承担"批量、周期性搬运"的角色，不解析任何 CAN 业务内容。

## 二、槽位报文格式

每个 PDO 槽位保存一条 14 字节的 CAN 报文，布局如下：

| 偏移 | 大小 | 内容 |
|---:|---:|---|
| 0 | 4 字节 | CAN 标识符 |
| 4 | 1 字节 | 帧属性（扩展帧、CAN FD、远程帧等标志） |
| 5 | 1 字节 | 有效数据长度（≤ 8） |
| 6 | 8 字节 | CAN 数据区 |

用最简单的结构示意该布局：

```c
/* 14 字节槽位：偏移 0..13 */
typedef struct __attribute__((packed)) {
    uint32_t can_id;   /* 0..3  CAN 标识符           */
    uint8_t  flags;    /* 4     帧属性               */
    uint8_t  len;      /* 5     有效数据长度          */
    uint8_t  data[8];  /* 6..13 数据区               */
} can_msg_slot_t;
```

帧属性字节中已定义的标志位：

| 位 | 含义 |
|---|---|
| bit0 | 扩展帧标识符（EFF），置 1 表示 29 位扩展 ID |
| bit1、bit2 | CAN FD 标志：两位同时置 1 表示 CAN FD 帧；全 0 为经典 CAN 帧 |
| bit3 | 远程请求帧（RTR） |

## 三、支持的数据布局

从站的输出 PDO 大小决定了它的总线数量与每条总线的槽位数。当前支持的布局：

| 网关类型 | 总线数 | 每总线每周期槽位数 | 附加字段 | PDO 大小 |
|---|---:|---:|---|---:|
| 经典 CAN 双总线 | 2 | 3 | 报文数量、扩展帧标志 | 86 B |
| 经典 CAN 八总线 | 8 | 3 | 报文数量、扩展帧标志、保留字节 | 340 B |
| CAN FD 八总线网关 | 8 | 8 | 无 | 896 B |
| CAN FD 八总线十槽网关 | 8 | 10 | 无 | 1120 B |
| CAN FD 三总线网关 | 3 | 8 | 无 | 336 B |

经典 CAN 布局的附加字段：

- **报文数量**：本周期实际装载的报文条数，从站据此判断哪些槽位有效；
- **扩展帧标志**：本周期报文使用标准帧还是扩展帧；
- **保留字节**：固定为 0，供后续扩展。

CAN FD 网关布局不携带数量字段：槽位要么有效（`len > 0`），要么是空槽位
（`len == 0`），接收侧只需忽略空槽位。

主站连接时根据从站实际输出 PDO 长度自动识别上表中的布局类型；无法识别的长度
将视为不支持的从站，不会建立通信。

## 四、总线与槽位的对应关系

槽位按**总线主序连续排列**：总线 0 的槽位排在最前，总线 1 紧随其后，依此类推；
每条总线内部的槽位数由第三节表决定。发送时先把报文放入对应总线区间内的空闲槽位，
接收时则根据槽位所在区间反推出总线号。

```c
/* 双总线经典布局：附加字段之后按总线顺序平铺槽位 */
typedef struct __attribute__((packed)) {
    uint8_t num;                /* 报文数量   */
    uint8_t ide;                /* 扩展帧标志 */
    can_msg_slot_t bus0[3];     /* 总线 0：3 个槽位 */
    can_msg_slot_t bus1[3];     /* 总线 1：3 个槽位 */
} classic_dual_bus_t;

/* CAN FD 八总线网关布局：无附加字段，槽位区从首字节开始 */
typedef struct __attribute__((packed)) {
    can_msg_slot_t bus0[8];     /* 总线 0：8 个槽位 */
    can_msg_slot_t bus1[8];     /* 总线 1：8 个槽位 */
    /* …… 依此类推，共 8 条总线 …… */
    can_msg_slot_t bus7[8];     /* 总线 7：8 个槽位 */
} fd_eight_bus_t;
```

用代码表达通用的槽位定位逻辑：

```c
/* 定位总线 bus_idx 的第 slot_idx 个槽位（slot_idx 从 0 计） */
size_t slot_base = bus_idx * slots_per_bus;      /* 槽位数组下标起点 */
size_t index     = slot_base + slot_idx;         /* 槽位数组下标     */
```

- **发送**：报文写入区间 `[bus_idx×N, bus_idx×N + N)` 内的第一个空槽位
  （`len == 0`），其中 `N` 为该布局每总线槽位数；
- **接收**：由槽位数组下标反推 `bus_idx = index / N`；
- 经典 CAN 布局的槽位区前有 2 字节附加字段（八总线布局在槽位区后另有 2 字节保留），
  CAN FD 布局无附加字段，槽位区从 PDO 首字节开始；
- 经典布局中，"报文数量"统计的是所有总线本周期实际写入的槽位总数。

## 五、收发逻辑

### 发送方向（主站 → 网关）

每周期开始时输出 PDO 被整体清零，然后逐条装载待发报文：

```text
对每条待发报文 msg：
    定位 msg 所属总线 bus_idx 的槽位区间
    在该区间内找第一个空槽位
    若找到：写入（经典布局同时递增报文数量）
    若区间已满：留到后续周期继续发送
```

- 同一总线的多条报文按序填入该总线的各槽位；
- 单周期放不下的报文自动顺延到**后续周期**，不会丢失；
- 输出 PDO 每周期整体清零后再装填，保证不会把上一周期的残留数据误发出去。

### 接收方向（网关 → 主站）

输入 PDO 按固定顺序扫描：

```text
对每个槽位：
    由槽位数组下标反推总线号 bus_idx
    len == 0  → 空槽位，忽略
    len >  0  → 还原为一条 CAN 报文，连同 bus_idx 交给上层
```

槽位在 PDO 中的位置即携带了总线信息，因此接收到的每条报文都能还原出它来自哪条
总线，无需额外的地址字段。
